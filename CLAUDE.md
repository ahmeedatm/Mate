# Hackathon Unowhy : compagnon de bureau sur tablette 4.2

### Le projet
Unowhy a des tablettes **Unowhy 4.2** (tablettes SQOOL) en stock (18 000 à valoriser, d'après la note projet UNOMATE), sous Android 8 à 11 selon les lots. **On cible Android 10** (celle d'Eliot, et l'image sans surcouche demandée). Un hackathon interne doit leur trouver une seconde vie. Elles sont peu puissantes : pas d'applis lourdes. Pas d'IA : l'Assistant IA a été abandonné le 26/10/2026.

### L'idée de départ (Eliot)
Un **compagnon de bureau** : la tablette posée sur le bureau, avec plusieurs modes :
- **Mode "Steam Deck" / sons** : interface média et ambiance (sons d'ambiance, contrôle audio, retours sonores, Bluetooth vers une enceinte). Interprétation à confirmer avec Eliot.
- **Autres usages de bureau** : timer / Pomodoro, agenda, météo, notifications, etc.

### Contraintes techniques connues
- Cible : **Android 10 (API 29)**, tests sur l'émulateur `companion_api29` puis la vraie tablette. `minSdk 24` est gardé (ne coûte rien, laisse tourner les lots en Android 8). Les `<queries>` du manifeste restent pour Android 11+.
- **Seul matériel cible** : spec relevée par adb dans `docs/tablette-4.2.md` (MT8167 4 × Cortex-A35 1,3 GHz, 2 Go de RAM, tas de 128 Mo, GPU PowerVR GE8300, écran 1280×800 à 55 Hz soit 18,2 ms par image, WebView 81, pas de vibreur). Toute décision technique se vérifie contre elle. Numéro de série commençant par 7733 = V4.2.
- Pas d'IA, ni locale ni cloud (Assistant IA retiré le 26/10/2026). La tablette est une interface : micro (commande vocale par la reconnaissance Android), écran, haut-parleur.
- Aucun secret (clé API) ne doit être stocké sur la tablette. Seule exception (27/10/2026) : le deploy token « tablettes-mises-a-jour », en lecture seule du registre de paquets du projet (`read_package_registry`), injecté par la CI dans l'APK release pour lire les mises à jour (variable `UPDATE_DEPLOY_TOKEN`).

### Architecture "client léger"
La tablette est l'interface ; le backend sur l'ordinateur pilote l'ordinateur. Aucune IA (Assistant IA retiré le 26/10/2026).

### Points à vérifier avant de coder (bloquants possibles)
1. **MDM** : vérifié par adb sur la tablette d'Eliot (23/10/2026, détails dans `docs/tablette-4.2.md`). Le système est un Android 10 Unowhy quasi standard (services Google, Play Store, Google TTS). Le MDM SQOOL (`com.hisqool.devicemanager`) est une appli installée dans `/data`, **profile owner** (pas device owner) ; seule restriction : `no_add_user`. adb et l'installation d'APK par adb fonctionnent déjà. Bloquant pour le kiosque seulement : `dpm set-device-owner` échoue tant qu'il y a un profile owner. Fait le 23/10/2026 (pas de reflash : bootloader verrouillé) : réinitialisation d'usine **hors ligne**, UnoMate device owner avant le WiFi ; il masque l'agent SQOOL de l'image (`com.unowhy.sqoolota`, qui réinstalle le MDM dès qu'il a du réseau) et bloque toute installation (Réglages > code technicien > Autoriser les installations : la carte Kiosque est cachée derrière un appui long sur le titre + code `BuildConfig.TECH_CODE`, 4242 par défaut ; micro et caméra accordés d'office). Procédure : `docs/kiosque.md`. L'appli n'a pas besoin des services Google ; elle utilise le WebView (« Page de l'ordi »), qu'elle met à jour elle-même (carte Mises à jour).

3. **Qualité micro / haut-parleur** intégrés : sinon dock avec micro/enceinte externe (USB ou Bluetooth).
4. **Débogage USB (adb)** activable ?
5. **Réseau** : WiFi sur le lieu du hackathon, accès sortant aux API cloud autorisé.

### Autres pistes si l'idée principale bloque

### Décisions techniques proposées (à valider)

- Dépendances minimales (APK léger, compat API 24).
- Test sur **tablette réelle** via adb dès le premier jour (l'émulateur ne reflète pas les perfs).

### Règles de travail
- Une question à la fois si une info manque, plutôt que deviner.
- Expliquer les choix en 1-2 phrases.
- Ne rien commit sans demande explicite.
- `main` protégée : tout passe par une branche et une MR, fusionnée seulement avec le pipeline vert (`.gitlab-ci.yml` : format prettier + typecheck + tests d'intégration backend sous seuil de couverture (`backend/.c8rc.json`), tests Playwright des pages web du backend, ktlint + tests JVM + APK Android ; rien de lourd en MR : ni émulateur, ni installation réelle, ni compilation Windows ; `npm run format` et `./gradlew ktlintFormat` avant de pousser ; voir `docs/developpement.md`). Nouveau comportement backend = un test dans `backend/test/` ; page web servie par le backend = un test dans `backend/e2e/` ; logique pure Android = un test dans `app/src/test/`. Release : tag `vX.Y.Z` sur `main` → paquets, APK signé (clé en variables CI protégées), release GitLab ; `versionName`/`versionCode` suivent le tag (`-PappVersion`) ; `npm run updates:add` alimente le « serveur Unowhy » (docs/developpement.md, section Release).
- Essais de MR en parallèle, sans fusion ni tag : branche protégée `essai/mr-<iid>`, job manuel `essai-android` (version `X.Y.Z-essai.N`, code entre deux tags : versionCode = (X × 10000 + Y × 100 + Z) × 1000), puis `essai-backend` (archive du backend Mac et Windows, sans node, seulement si `backend/` change par rapport à `main`) et `essai-updates` (`scripts/updates-publish.mjs --essai`, `resource_group`) : paquet commun `companion-updates/essais` (jamais `latest`), une entrée par MR dans son `manifest.json` (MR, titre = variable de pipeline `MR_TITLE`, version, APK, backends) ; fusion ou abandon : `essai.sh --retire <iid>` (docs/developpement.md, section Release). L'essai est une autre appli, `com.unowhy.companion.essai` « UnoMate essai » (`-essai.N` → `applicationIdSuffix`, `BuildConfig.TRIAL`), une seule installée à côté de la stable, qui reste device owner : Réglages > Mises à jour liste les essais par MR lus dans le registre (jeton de lecture déjà injecté, sans passer par l'ordinateur), choisir une MR installe son essai à la place du précédent (désinstallé d'abord si sa `versionCode` est plus basse), l'autorise en lock task et l'ouvre (« Ouvrir l'essai ») ; l'essai reprend ses ordinateurs par `trial/ComputersProvider` (permission signature, jamais de jeton dans un intent ou un fichier) et rend la main (« Revenir à la stable »). Backend d'une MR : la tablette télécharge l'archive de la plateforme de l'ordinateur actif (taille et SHA-256 vérifiés) et l'envoie à son backend (`POST /companion/backend/essai`, jeton d'appairage ; `backend/src/essai-backend.ts` garde une seule copie d'origine, remplace sans node ni lanceur Windows, redémarre ; `POST /companion/backend/origin` restaure) ; installé par paquet seulement, lancé depuis le dépôt il refuse (409) ; restauré par « Revenir à la stable », au retour de la stable, et par une MR sans backend ; package `trial/` (`EssaiBackend`, `EssaiPlan`).
- Installation, `backend/src/mac/`, `backend/src/win/` ou `service.ts` touchés : tests d'installation à la main (`backend/qa/install-mac.sh`, `install-windows.ps1`, `npm run build:helper` ; docs/developpement.md, section Branches, MR et CI) ; paquets et `helper-windows` ne tournent que sur un tag.
- CI ciblée par zone (`rules:changes` en MR, tout sur main et les tags ; pas de nightly) ; `backend/qa/sanity.ts` = un contrôle par feature contre un compagnon réel, lancé par les scripts d'installation ; nouvelle feature backend = un contrôle dans la sanity ; voir docs/developpement.md, section Branches, MR et CI.
