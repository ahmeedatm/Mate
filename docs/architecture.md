# Comment ça marche

Pour comprendre le projet avant d'y toucher. Installation et commandes : [README](../README.md) ; travailler dessus : [developpement.md](developpement.md) ; où on en est : [etat-du-projet.md](etat-du-projet.md).

## L'idée en une phrase

Une tablette 4.2 (Android 10, lente) posée à côté de l'ordinateur sert d'écran de contrôle : tableau de bord, Stream Deck, fenêtres, son, agenda, tâches, visualiseur de documents. **La tablette ne fait que l'interface.** Tout ce qui agit sur l'ordinateur (lancer une appli, taper un raccourci, lire l'agenda, bouger une fenêtre) est fait par un petit programme installé sur l'ordinateur : le « compagnon » (dossier `backend/`).

```
┌────────────── Tablette (app/) ──────────────┐            ┌──────── Ordinateur Mac ou Windows (backend/) ────────┐
│ Appli Android Kotlin, en kiosque            │  WiFi      │ Node 22 + Fastify, port 3000                          │
│ MainActivity + un Fragment par mode         │ ─HTTP────▶ │ server.ts : jeton ; routes/ : routes par domaine      │
│ BackendClient (HttpURLConnection)           │  + jeton   │ deck.ts → os.ts ─┬─ mac/ (osascript, JXA)             │
│ RemoteChannel (long-polling) ◀──────────────│─ ordres ── │ tablet.ts (file   └─ win/ (MateHelper.exe, C#)      │
│ Discovery (UDP) ◀──────── diffusion ────────│─ UDP ───── │   d'ordres)        calendar, tasks, events, camera…   │
└─────────────────────────────────────────────┘            │ .data/ : données de cet ordinateur                   │
        │ MET Norway (météo, sans clé)                     └───────────────────────────────────────────────────────┘
        ▼                                                     ▲ mcp.ts (Claude Code / Desktop) relaie vers /tablet/command
```

Pas de serveur dans le cloud : chaque ordinateur a son compagnon, la tablette parle directement à celui qu'elle pilote. Seules les mises à jour passent par Internet : la tablette les lit dans les releases GitHub du projet (le compagnon peut aussi servir les siennes). Pas d'IA : l'Assistant IA a été retiré le 26/10/2026.

## Les deux programmes

### La tablette (`app/`)

- **Une seule Activity** (`MainActivity`) plein écran, barre fixe à gauche (Parler, profils Accueil / Deck / Réunion pendant un appel, outils, ordinateur, Réglages ; heure, WiFi, batterie et lecture en cours en haut à droite), un **Fragment par mode** : Profils (ex-Accueil), Deck, Depuis l'ordi, Focus, Caméra, Réglages. Les fragments sont créés une fois et cachés/montrés ; ils sont recréés quand on change d'ordinateur (`onComputerChanged`).
- **Panneau document** (`DocumentPanel`) à droite : document du dossier partagé ou page web de l'ordinateur, à côté de n'importe quel mode ou en grand.
- **Kiosque** : l'appli est *device owner* (installée sur une tablette réinitialisée, voir [kiosque.md](kiosque.md)). Elle verrouille l'écran sur elle-même (lock task), masque l'agent de provisionnement du constructeur, bloque les installations, s'installe elle-même ses mises à jour et règle le WiFi.
- Vues XML, pas de Compose ; dépendances : appcompat, lifecycle, coroutines. HTTP par `HttpURLConnection` + `org.json`. Tout doit rester léger (MT8167, 2 Go de RAM).

### Le compagnon de l'ordinateur (`backend/`)

- **Node 22, TypeScript lancé par `tsx`** (pas de compilation), **Fastify**. Appli portable, sans installation : l'exe Windows (`src/win/Mate.exe` + zip du runtime) ou `Mate.app` extrait son runtime dans le dossier de l'utilisateur, lance le serveur et le relance s'il s'arrête (sortie 75 = quitter, 76 = tout oublier). Le lancement à l'ouverture de session est une case du panneau (`src/portable.ts` : clé Run sous Windows, LaunchAgent sous Mac), rien n'est inscrit avant. Depuis le dépôt : `scripts/service.ts`.
- **`server.ts`** vérifie le jeton `Authorization: Bearer`, traduit les erreurs, enregistre les routes et lance les tâches de fond. Les routes (contrat de l'API) sont dans **`routes/`**, un plugin Fastify par domaine (`pairing.ts` pour `/health` et `/pair/*`, `local.ts`, `portable.ts` (carte « Cette appli » du panneau), `deck.ts`, `windows.ts`, `system.ts`, `docs.ts`, `browser.ts`, `camera.ts`, `calendar.ts`, `tasks.ts`, `calls.ts`, `tablet.ts`, `updates.ts`) ; les hooks posés dans `server.ts` valent pour tous. Sans jeton : `/health`, `/pair/*`, la page locale `GET /` (seulement depuis l'ordinateur).
- **`os.ts`** est le seul point d'entrée vers le système : il appelle `mac/` ou `win/` selon l'OS. Ajouter une action système = l'écrire dans les deux.
  - **Mac** (`src/mac/`) : `osascript` en AppleScript ou JXA. Frappes en CGEvent (System Events refuse les saisies), fenêtres par l'Accessibilité + NSScreen + CoreGraphics. Demande l'autorisation Accessibilité.
  - **Windows** (`src/win/`) : un **programme résident `MateHelper.exe`** (C# .NET Framework 4.8, compilé d'avance : `helper/Native*.cs` pour fenêtres, son, frappes, une classe partielle découpée par thème ; `helper/Program.cs` pour l'UI Automation ; `helper/Media.cs` pour les contrôles multimédias WinRT). `helper.ts` lui envoie des commandes JSON ligne par ligne. L'exe est copié dans `%LOCALAPPDATA%\Mate\helper` avant lancement pour ne pas verrouiller l'original. Pas de PowerShell : un script qui compile du C# de frappes à la volée était classé malveillant par Bitdefender.
- **`.data/`** (non versionné) : tout ce qui est propre à cet ordinateur (voir « Où sont les données »).

## Les flux principaux

### 1. Appairage et découverte

1. Le compagnon crée au premier lancement son identité et son jeton (`.data/identity.json`) et répond à une diffusion UDP sur le WiFi (`pairing.ts`).
2. La tablette cherche les ordinateurs (`net/Discovery.kt`), ou on saisit l'adresse.
3. En WiFi, tout passe en HTTPS (certificat auto-signé de l'ordinateur, `tls.ts`) ; le HTTP n'écoute que sur 127.0.0.1. La tablette affiche un code à 6 chiffres, qui mêle l'empreinte du certificat qu'elle voit ; l'utilisateur le saisit sur l'ordinateur (page `http://127.0.0.1:3000/`), la tablette reçoit le jeton et épingle le certificat. Détails et protocole : [securite-appairage.md](securite-appairage.md).
4. La tablette garde une **liste d'ordinateurs** (`Computers.kt` : id, nom, url, jeton, os, empreinte épinglée) et pilote l'actif. Si l'actif ne répond plus, `net/Connection.kt` retrouve sa nouvelle adresse par la recherche, ou bascule vers un autre ordinateur qui répond.
5. **Plugins** (première utilisation) : le compagnon propose ses plugins (`plugins.ts`, `GET /plugins`) : applis trouvées sur l'ordinateur (Discord, Teams, Claude Code) et fonctions intégrées (Ouvertes, Son, Pavé, Média). La tablette ouvre l'écran des plugins (`PluginsView`) tant qu'un plugin n'a jamais été proposé : au premier appairage, et quand une appli compatible apparaît ensuite. Les choix (`POST /plugins`, `.data/plugins.json`) valent pour cet ordinateur. Un plugin coupé : sa page disparaît du deck (`/deck`), ses appels ne sonnent plus, ses onglets sont masqués (`off` de `/deck/features`). Jamais choisi = actif. Rouvrable dans Réglages > Plugins.

### 2. Une requête ordinaire (tablette → ordinateur)

`BackendClient` envoie du JSON avec le jeton ; les erreurs sont traduites en phrase par `errorText(e)` (`ui/Errors.kt`), jamais affichées brutes. Côté compagnon, `setErrorHandler` remplace les erreurs techniques par une phrase en français.

### 3. Les ordres de l'ordinateur vers la tablette (canal `/tablet`)

La tablette n'ouvre aucun port. `remote/RemoteChannel.kt` garde une requête `POST /tablet/poll` ouverte (long-polling) ; le compagnon y dépose les ordres (`tablet.ts`) : rappel parlé d'une tâche ou d'un événement, message, changement de mode, capture d'écran, sonnerie pour retrouver la tablette (ordre `ring`, `audio/Ringer.kt` : son d'alarme au maximum en boucle, volume remis ensuite ; un toucher, l'ordre inverse ou 2 minutes l'arrêtent ; bouton « Faire sonner » du panneau Tablette et outil `tablette_sonner`)… Livraison « au moins une fois », dédoublonnée par la tablette. C'est aussi par là que passe **l'extension Claude** (`mcp.ts`, serveur MCP qui relaie vers `POST /tablet/command`). Si l'écran de la tablette est éteint, l'appli est en pause et les ordres attendent.

### 4. Le Deck

- Les touches sont définies **uniquement côté ordinateur** : `config/deck.json` (départ copié de `deck.example.json` ou `deck.example.windows.json`, filtré aux applis installées), touches perso (`.data/keys.json`, `perso.ts`), applis ajoutées (`.data/apps.json`), sites de la page Média (`.data/links.json`).
- La tablette reçoit les pages (`GET /deck`) et n'envoie qu'un **identifiant de touche** ; `runAction` (`deck.ts`) exécute les étapes (app, keys, text, url, media, system, wait, window, macro, cycle). Aucune commande arbitraire ne vient de la tablette.
- **Seconde action (appui long)** : une touche de `config/deck.json` peut porter `hold` (une action, comme `action`). `GET /deck` donne `hold: true` ; `POST /deck/run` avec `hold: true` lance cette action (409 sans `hold`). Dans le widget Touches, l'appui long d'une touche qui en a une la lance ; sans elle, il propose de la retirer du widget. Une touche perso (`keys.json`) porte `hold` : une liste d'étapes (une = raccourci simple, plusieurs = macro), réglée dans l'éditeur par la pastille « Seconde action (appui long) ». L'éditeur d'une touche s'ouvre seulement en mode Modifier (réglages du widget Touches, bouton « Modifier » en face d'une touche perso), plus à l'appui long ; « Nouvelle touche » ouvre toujours l'éditeur. L'outil MCP `deck_touche` et la page locale ne règlent pas `hold` (la page locale le garde tel quel à l'enregistrement).
- Onglets : pages fixes, puis pages d'appli (Discord, Réunion) tant que l'appli tourne ou est en appel (`GET /deck/live`). On change d'onglet en touchant ou en balayant la grille.
- **Ouvertes** : toutes les fenêtres de l'ordinateur sur le schéma de ses écrans (`OpenWindowsView` + `ScreenMap`, `GET/POST /windows/open`), relu toutes les 5 s.
- **Média** (Windows et Mac) : lecture en cours lue dans les contrôles multimédias de Windows (`/system/media`) ou, sur Mac, par MediaRemote (« À l'écoute », `src/mac/media.ts` + `NowPlaying.dylib` chargée par `/usr/bin/perl`, seul accès possible depuis macOS 15.4 : risque qu'Apple le ferme, secours par les titres d'onglets) ; musique ouverte dans l'appli du site si elle est installée, sinon le site (`music.ts`). Sur Mac, les commandes passent par l'extension du navigateur qui joue quand elle est chargée (dans la page : lecteur, actions Media Session), sinon par MediaRemote.

### 5. Agenda, tâches, rappels

- Agenda (`calendar.ts`) = liens ICS (`.data/calendar.json`) + comptes Microsoft/Google (`accounts.ts`, OAuth, pas encore activé : identifiant d'appli à obtenir) + agenda personnel noté depuis la tablette (`events.ts`). Réunions en ligne détectées dans les événements (`meeting-links.ts`), ouvertes sur l'ordinateur par `POST /calendar/join`.
- Tâches (`tasks.ts`) : ponctuelles, récurrentes (créées depuis la tablette), ou quotidiennes écrites dans `config/tasks.json` (exemple : saisir son temps dans Jira, cochée seule via `jira.ts`). Les rappels partent de l'ordinateur par le canal `/tablet` et sont lus à voix haute par la tablette (`audio/Speaker`).
- Onglet Jira du Deck (`routes/jira.ts`, tablette `ui/JiraView`, `net/JiraApi`) : tickets assignés en colonnes : l'union des colonnes des tableaux Jira choisis sur la tablette (API Agile, `GET/POST /jira/boards`, choix dans `.data/jira.json`), terminés des 7 derniers jours compris, ticket placé par l'id de son statut ; sans tableau choisi, une colonne par statut (à faire puis en cours). Toucher un ticket = ses transitions Jira ; une transition qui demande un champ (`needsJira`, ou Jira répond 400 → 409) se finit dans Jira, ouvert sur l'ordinateur. Proposé seulement si Jira est configuré (`/deck/features` → `jira`).
- Eau et Focus (Pomodoro, ambiance) sont **sur la tablette seulement** (`focus/`).

### 6. Visualiseur (mode Caméra)

`camera/DocCamera.kt` (Camera2) envoie du JPEG 720p à ~10 i/s à `POST /camera/frame` ; le compagnon garde la dernière image et la sert en MJPEG sur `http://127.0.0.1:3000/camera`, à projeter. « Envoyer une photo » : photo pleine taille dans le dossier Partage.

### 7. Cadre photo

Après quelques minutes sans toucher (Depuis l'ordi > Cadre photo, `ui/FrameSettingsView` : 2, 5, 10 ou 30 min, ou jamais ; vignettes, Ouvrir le dossier sur l'ordi, Essayer), les photos du dossier « Cadre photo » du dossier partagé défilent en plein écran, l'heure et la date en bas (`ui/PhotoFrameView`, lancé par `MainActivity.followFrame` à chaque minute) ; un toucher revient à l'écran sans agir dessous. `GET /frame` (`docs.ts`) liste les images (JPEG, PNG, WebP, sous-dossiers compris, 500 au plus) ; `frame/FrameCache` les copie une fois par `/docs/file`, réduites à la taille de l'écran et remises droites (EXIF), un dossier par ordinateur : le cadre marche ordinateur éteint. Économie (`frame/FrameLogic`) : luminosité plafonnée à 35 % (20 % sur batterie), image fixe entre deux fondus de 600 ms, écrans dessous masqués, arrêt la nuit (atténuation) et sous 20 % de batterie débranchée ; pas de cadre pendant un appel, une question d'agent, le Focus qui tourne, la Caméra ou un document ouvert.

### 7. Commande vocale (bouton Parler)

Pas d'IA : la reconnaissance est celle d'Android (`SpeechRecognizer`, servie par l'appli Google de l'image d'usine : en ligne, sans clé ni compte ; à ne pas désactiver dans la procédure de kiosque). La phrase est comprise **sur la tablette** par une liste de tournures (`voice/VoiceCommands.kt`) : modes, son et micro, musique, Focus, ambiance, fenêtres (comme l'onglet Ouvertes), tâches et journée, rappels, recherche, dictée (`POST /system/type`), copie sur l'ordi (« copie sur l'ordi … » ou « copie ça sur l'ordi … » → `POST /system/clipboard`), appels ; puis toute touche du Deck par son nom, puis toute appli installée (`POST /apps/launch`). Les noms d'applis mal entendus sont rapprochés à l'oreille (prononciation approximative + distance d'édition, sur les 5 variantes du reconnaisseur : « en cabane launcher » → Ankama Launcher). `voice/VoiceControl.kt` écoute et exécute ; appui long = commande écrite (émulateur sans reconnaissance). Journal : `adb logcat -s Voice` (niveau info : la tablette jette le debug).

### 8. Appels entrants (Windows, Mac)

`calls.ts` lit le titre des fenêtres toutes les 2 s (« Appel entrant - Discord »), puis l'interface une fois pour le nom de l'appelant, et prévient la tablette par le canal `/tablet` (ordre `call`). `ui/CallOverlay.kt` : carte Répondre / Vidéo / Ignorer, qui appuient sur les vrais boutons (`/calls/answer`, `/calls/decline`, UI Automation) ; Répondre ouvre la page de l'appli dans le Deck ; « Appel manqué » sinon. Règles par appli dans `config/calls.json` (titre, appelant, noms des boutons) : une appli de plus = une capture pendant un vrai appel (`GET /deck/buttons?app=…&detail=true`). Windows : Discord. Mac (`src/mac/calls.ts`, API d'Accessibilité) : la sonnerie se voit aux boutons (`ring`), le titre de la fenêtre ne change pas ; Teams (boîte de « Microsoft Teams (Notification Center) ») et Discord (appelant dans le lien de la conversation, « Lien : … (message de groupe), 3 membres, Appel entrant »). Discord (Electron) n'ouvre son arbre qu'avec `AXManualAccessibility` posé en `NSNumber` (`kCFBooleanTrue` est ignoré, sans relancer l'appli), Teams avec `AXEnhancedUserInterface`. Page Discord pendant l'appel sur Mac : `discordStateOf` (salon, participants, micro, sourdine), comme `Voice` de `helper/Program.cs`. Fenêtre de Discord sur un autre bureau ou fermée : rien n'est lu (l'Accessibilité ne voit que le bureau affiché).

### 9. Mises à jour de la tablette

Deux sources, même format (`{"updates":[{package, label, versionCode, versionName, file, size, sha256}]}`) :

- **L'ordinateur relié** (serveur simulé par le backend, `updates.ts` : `.data/updates/manifest.json` + APK), avec le jeton d'appairage. Il sert aussi le WebView.
- **GitHub** : assets de la release `latest` du dépôt privé `BuildConfig.UPDATE_REPO` (`manifest.json` puis chaque fichier), lus par l'API GitHub (`net/GitHubReleases.kt`) avec `BuildConfig.UPDATE_TOKEN`, jeton en lecture seule injecté au build release (vide en debug), jamais envoyé à un autre hôte que `api.github.com`. Marche sans ordinateur. Rien de publié ou accès refusé (401, 404) : « aucune mise à jour », pas d'erreur. `-PupdateUrl=` remplace GitHub par un serveur HTTP simple (essai local).

`kiosk/Updater.kt` interroge les deux en parallèle et fusionne (`kiosk/UpdatePlan.kt` : par paquet, la plus haute `versionCode` ; à égalité, l'ordinateur). Il télécharge, vérifie le SHA-256 et installe en silence (device owner), une installation à la fois. `kiosk/AutoUpdater.kt` vérifie au démarrage puis toutes les 6 h (échéance relue tous les quarts d'heure) et installe seul la release `latest` la plus récente du Mate (jamais un essai), en device owner seulement, sans rien afficher. La carte Mises à jour de Réglages montre les deux sources (une version plus basse que l'installée est marquée non installable, Android la refuserait ; une ligne par source en erreur) puis, dessous, les essais de PR (voir plus bas). `kiosk/UpdatedReceiver` relance l'appli en kiosque après sa propre mise à jour.

**Essai d'une PR** (`trial/`) : une version `X.Y.Z-essai.N` est une autre appli, `app.mate.essai` « Mate essai » (`applicationIdSuffix`, `BuildConfig.TRIAL`, `app/build.gradle.kts`), signée par la même clé et installée à côté de la stable. La stable reste device owner. Les essais de toutes les PR sont publiés dans la release `essais`, un manifest `{"essais":[…]}` à une entrée par PR (`net/UpdatesApi.essais()` : même dépôt et même jeton de lecture, tag `essais`, sans passer par l'ordinateur ; `Updater.essais`, source `UpdateSource.TRIALS`). Réglages > Mises à jour les liste (« #109 titre », version, backend remplacé ou non) ; choisir une PR installe son essai à la place du précédent (`AutoUpdater` ne prend que son propre paquet), en le désinstallant d'abord, sans confirmation, si sa `versionCode` est plus basse (`EssaiPlan.install`, `Updater.uninstall`), puis met le backend de l'ordinateur actif sur celui de la PR (`EssaiBackend.sync`). La stable autorise l'essai en lock task (`setLockTaskPackages`), lui accorde micro et caméra, et l'ouvre (« Ouvrir l'essai » : relit le backend de la PR installée, `Prefs.trialMr`, et le remet si l'ordinateur n'y est plus). L'essai, jamais device owner, se verrouille seul si la stable l'y autorise (`isLockTaskPermitted`) et rend la main par « Revenir à la stable » (il restaure le backend d'origine de l'ordinateur, puis se ferme ; la stable, à son retour, le refait si l'essai a planté : `Prefs.trialOpened`). Au premier lancement, il reprend la liste des ordinateurs de la stable, jetons compris, sans réappairer : `trial/ComputersProvider` de la stable, exporté sous la permission `app.mate.permission.COMPUTERS` de niveau signature (Android refuse toute appli d'une autre clé) ; ensuite chacune garde sa liste. Une seule des deux tourne au premier plan : le canal `/tablet` ne vit que pendant `STARTED`, pas de conflit sur l'ordinateur.

**Backend d'une PR sur l'ordinateur** (`backend/src/essai-backend.ts`, routes dans `routes/updates.ts`) : la tablette télécharge dans la release `essais` l'archive de la plateforme de l'ordinateur (`backend-<version>-mac|windows.tar.gz`, backend sans node ni lanceur Windows, fabriqué par `npm run package -- essai`), vérifie taille et SHA-256, et l'envoie (`POST /companion/backend/essai?mr=&sha256=`, jeton d'appairage : aucun secret ne va à l'ordinateur). L'ordinateur extrait à part, vérifie, garde une seule copie de son backend installé (`<données>/backend-origin`, jamais écrasée par un essai suivant), remplace `dist/`, `src/`, `scripts/`, `assets/` et les fichiers livrés de `config/` (pas `node/`, le lanceur, `.env`, `deck.json`, `tasks.json`), écrit `essai-backend.json` et redémarre. `GET /companion/backend` donne l'état, `POST /companion/backend/origin` restaure. Compagnon lancé depuis le dépôt : 409, l'essai du backend marche seulement avec le paquet. Détails : `docs/developpement.md`, « Déployer un essai depuis une PR ».

### 10. Agents Claude (Mac)

La tablette montre les sessions Claude Code de l'ordinateur (qui travaille, qui a fini, qui attend) et y répond. `agents.ts` tient l'état par `session_id`, en mémoire, de trois sources : `claude agents --json` (toutes les 4 s, seulement tablette connectée : le filet), les hooks HTTP de Claude Code (`POST /agents/hook`, local, secret propre dans `.data/agents-hook.json`, posés par `npm run agents:hooks`) et `orca worktree ps --json` si Orca est là (branche, terminal). États : travaille, attend, fini, limite, inactif. La tablette est prévenue par l'ordre `agent` du canal `/tablet` (lumière de bord et son), sauf si l'appli de devant est un terminal ou Orca : l'utilisateur n'est alors pas prévenu. Répondre : le hook `PermissionRequest` (permission) ou `PreToolUse` sur `AskUserQuestion` (question à choix) reste ouvert jusqu'à `POST /agents/answer` ou `AGENTS_HOLD_S` (90 s), puis reçoit `{}` : le terminal décide. Sur la tablette, la carte de la demande (`AgentAskOverlay`) s'ouvre en touchant la lumière de bord ou une session de l'onglet : permission (Autoriser une fois / Refuser ; une commande à risque, `isRisky` côté compagnon, s'autorise en maintenant le bouton) ou questions à choix, une page par question, multi-choix, « Autre » écrit ou dicté. Sur une session au repos dans un terminal Orca (volet exact donné par `$ORCA_PANE_KEY` en en-tête du hook, terminal par `orca terminal list`), « continue » ou une phrase partent par `POST /agents/send` (`orca terminal send`) ; après une limite d'usage (`StopFailure` `rate_limit`), la tablette peut armer l'envoi de « continue » à l'heure de reprise lue dans le message. Les sessions de chat Orca et les terminaux ordinaires n'ont pas de moyen fiable : pas de bouton. Toucher une session l'amène devant : son terminal (`orca terminal switch`), sinon son chat Orca (worktree et onglet `agent-session:<id>` activés par le client du runtime d'Orca, la CLI ne sachant pas le faire), sinon Orca seulement. Par l'extension MCP, Claude lit lui-même l'état des autres sessions (`agents_lister`) et peut poser une question à choix sur la tablette (`tablette_demander`, `POST /agents/ask-tablet`) : même carte, réponse renvoyée comme résultat d'outil. Interrompre une session (Échap dans son terminal Orca, après confirmation) et usage Claude du compte 5 h / 7 j (lu dans Orca, `rateLimits.claude` de `accounts.list` ; à défaut, statusline enveloppée par `agents:hooks --statusline`, seul `rate_limits` est lu) complètent l'onglet. Jamais de décision sans action sur la tablette, ni « toujours autoriser ». Détails et essais : [recherche-agents-claude.md](recherche-agents-claude.md).

### 11. Verrou de la tablette

Deux verrous indépendants, écran plein dans sa propre fenêtre par-dessus tout (`ui/LockScreen`, logique `lock/LockLogic`), gardés dans les préférences (tenus hors ligne et après une relance) :

- **Ordinateur verrouillé** : le compagnon relit la session chaque seconde (`screen-lock.ts` ; Mac : `IOConsoleUsers` d'`ioreg`, `mac/lock.ts` ; Windows : op `locked` du helper, `WTSQuerySessionInformation`). Verrouillée, ou prise par un autre utilisateur : toute route à jeton répond 423 sauf `/tablet/poll|result`, le pavé UDP est ignoré, les ordres de contenu ne partent plus (rappels redonnés après), les demandes d'agents reviennent tout de suite au terminal. La tablette apprend l'état par l'ordre `lock` (ou un 423), l'annonce dans l'état de son poll (`locked`) ; le compagnon la corrige à chaque tour si elle ne montre pas le bon. Ordinateur injoignable : elle reste bloquée. Réglages > Tablette > « Bloquer la tablette quand l'ordinateur est verrouillé » (`Prefs.blockOnComputerLock`, activé par défaut) : coupé, pas d'écran plein (`LockLogic.kind`), la tablette reste utilisable ; elle garde et annonce l'état comme avant, la pastille de la barre dit « verrouillé » (anneau, `linkMark`) et une action refusée affiche « <nom> est verrouillé » (`errorText`, 423). Le compagnon ne change pas.
- **À la main** : cadenas du pied de la barre ; code à 4 chiffres (empreinte salée) choisi au premier verrouillage ou dans Réglages > Tablette ; 5 codes faux = 30 s d'attente. Le déverrouillage du Mac ne le lève pas.

Sortie de secours : appui long, puis code technicien (lève les deux ; un ordinateur joignable et verrouillé reprend la main au tour suivant). Instance de test (`COMPANION_HEADLESS`) : jamais verrouillée.

## Ajouter une fonction : les recettes

- **Nouvelle route** : la déclarer dans le plugin de son domaine sous `routes/` (avec son schéma ; nouveau plugin = `app.register` dans `server.ts`), l'appeler dans le client de son domaine (`net/*Api.kt`). Erreur pour l'utilisateur = `throw new Error("phrase en français")`.
- **Nouvelle action système** : l'ajouter à `os.ts`, l'écrire dans `mac/` **et** `win/` (C# 7.3 dans `win/helper/`, `Native.<thème>.cs` pour le pilotage, puis `npm run build:helper`).
- **Nouvelle étape de touche** : type dans `deck.ts` (`runAction`), et dans `KeyEditor` si elle se règle depuis la tablette.
- **Nouvel ordre vers la tablette** : type dans `tablet.ts` + schéma dans `routes/tablet.ts` + outil dans `mcp-tools.ts` + branche dans `RemoteChannel.execute`.
- **Nouveau widget d'Accueil (Profils)** : le déclarer dans `WidgetModel`, le construire dans `HomeWidgets` (ou un fichier dédié de `ui/home/`).
- **Nouveau texte** : `strings.xml`, en français, court (la tablette est lue de loin), « ordinateur » (« ordi » sur les boutons courts).

Les conventions transverses sont dans [CLAUDE.md](../CLAUDE.md), section « Conventions du code » ; les conventions détaillées (noms historiques `Mac*` = l'ordinateur, Mac ou Windows ; clavier ; dialogues ; pièges de l'UI) sont dans la section « Détail par fonction » ci-dessous, tenue à jour à chaque changement.

### Performances

- **Performances** (`GET /system/perf`, `backend/src/perf.ts` pur, sources injectées par `os.ts`) : `cpu` et `ram` toujours, puis des champs facultatifs, absents quand ils sont illisibles et jamais inventés : `cpuTempC` (31/10 : entier 10–150 °C ; Mac Apple Silicon par `macmon pipe` (`src/mac/temperature.ts`, github.com/vladkens/macmon, MIT, sans `sudo`, à installer par `brew install macmon`, absent : rien) ; Windows par `MateCapteurs.exe` (`src/win/capteurs/`, LibreHardwareMonitorLib 0.9.6, MPL-2.0) qui écrit `%LOCALAPPDATA%\Mate\capteurs\cpu-temp.json` toutes les 2 s, lu par `src/win/capteurs.ts` (fichier de plus de 6 s : rien). Le pilote noyau PawnIO ne se lit qu'en administrateur : `scripts/capteurs-windows.ps1`, lancé par le bouton « Activer » du panneau (`POST /local/capteurs`, accord administrateur demandé une seule fois), installe PawnIO 2.2.0 (SHA-256 figé) et crée la tâche planifiée « MateCapteurs » (droits maximum, à l'ouverture de session) ; le compagnon la relance (`schtasks /run`, sans accord) quand le fichier est périmé), `fps` (31/10, #21 ; Windows avec carte AMD seulement : nombre entier du jeu au premier plan, `null` quand le lecteur marche mais qu'aucun jeu n'est mesuré, jamais 0 ; clé absente ailleurs, Mac compris, aucun moyen public d'y lire les FPS d'une autre appli). Lu par ADLX, le SDK d'AMD : `Native.Fps.cs` charge `amdadlx64.dll` du dossier système (installée avec le pilote, rien n'est livré) et appelle `IADLXPerformanceMonitoringServices::GetCurrentFPS`, le chiffre de l'overlay d'Adrenalin ; ne marche que dans la session de l'utilisateur, pas en SSH), `cpuWatts`, `gpuWatts` (W, une décimale, 0 à 1000 exclu 0 ; 01/11, #70 : Mac par `cpu_power` et `gpu_power` de la même lecture `macmon pipe`, partagée une seconde avec la température ; Windows par `MateCapteurs.exe` qui y ajoute « CPU Package » et le premier capteur Power d'une carte graphique, `gpuWatts` au niveau du relevé car le Mac n'a pas d'objet `gpu`), `cpuFanRpm` (tr/min entiers ; Windows seulement, ventilateur « CPU Fan » ou « CPU » de la puce Super I/O de la carte mère, donc absent sur les cartes dont LibreHardwareMonitor ne nomme que « Fan #1 » (on ne devine pas) ; 0 écarté ; absent sur Mac, `macmon` ne lit aucun ventilateur), `cpuMhz` (Windows, compteur PDH `Processor Frequency`), `gpu.vramUsedMb`/`vramTotalMb` (carte dédiée seulement : total DXGI, utilisé par le compteur `GPU Adapter Memory` du LUID de la carte), `disk` (`freeGb`/`totalGb` par `fs.statfs` de `/` ou `C:\`, `activity` 0-100 par `PhysicalDisk(_Total)\% Disk Time` sous Windows) et `net` (`upKBps`/`downKBps` : compteurs `Network Interface` sous Windows, deltas de `netstat -ib` sur les `en*` sur Mac). Chaque lecture est bornée à 1,5 s et normalisée (entiers, bornes, NaN et négatifs écartés). Windows : l'opération générique `counters` du pilote (`Native.Perf.cs`) lit une liste de chemins PDH anglais et rend la somme des instances valides (boucle locale et `isatap` exclues).
- **Courbe du widget** (01/11, #71) : taille Moyen seulement ; `PerfHistory` garde 150 relevés (un toutes les 2 s, soit 5 minutes) de processeur, carte graphique et mémoire, vidés quand la page est quittée ; `PerfSparkline` trace un trait par info cochée (processeur `c_text`, carte graphique `c_text_faint`, mémoire `c_text_dim`), de 0 à 100 %.
- **Choix des infos du widget** (31/10, #19) : dans le mode Modifier, le ⚙ du widget ouvre une liste à cocher par groupe (processeur, carte graphique, mémoire, disque, réseau, jeu), `PerfOption` / `PerfChoice` (`ui/home/PerfChoice.kt`). Le choix est gardé dans la config du widget posé, clé `perf` : un tableau de clés **par identifiant d'ordinateur** (les mesures lisibles diffèrent d'un ordinateur à l'autre) ; sans choix, l'affichage d'avant (CPU, GPU, RAM, température et ventilateur). Utilisation CPU, GPU et RAM gardent anneau, barre et chiffre ; toutes les autres infos passent en texte sur une ligne (Bandeau : une par ligne). À l'ouverture, un relevé dit quelles options sont lisibles : une option que l'ordinateur ne donne pas est grisée et décochée (« indisponible »), et reste dans le choix pour revenir si elle devient lisible. Températures du processeur (#20) et images par seconde (#21) sont lues : l'option FPS (`PcPerf.fpsReadable`, vraie dès que la clé `fps` est dans la mesure) est grisée « carte AMD sous Windows seulement » sinon ; sans jeu mesuré le widget écrit « — FPS », jamais 0. Pas de consommation de la carte graphique (unité de `D3DKMT_ADAPTER_PERFDATA.Power` non établie) ; batterie et temps depuis le démarrage sont hors sujet.
