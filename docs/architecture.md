# Comment ça marche

Pour comprendre le projet avant d'y toucher. Installation et commandes : [README](../README.md) ; travailler dessus : [developpement.md](developpement.md) ; où on en est : [etat-du-projet.md](etat-du-projet.md).

## L'idée en une phrase

Une tablette 4.2 (Android 10, lente) posée à côté de l'ordinateur sert d'écran de contrôle : tableau de bord, Stream Deck, fenêtres, son, agenda, tâches, visualiseur de documents. **La tablette ne fait que l'interface.** Tout ce qui agit sur l'ordinateur (lancer une appli, taper un raccourci, lire l'agenda, bouger une fenêtre) est fait par un petit programme installé sur l'ordinateur : le « compagnon » (dossier `backend/`).

```
┌────────────── Tablette (app/) ──────────────┐            ┌──────── Ordinateur Mac ou Windows (backend/) ────────┐
│ Appli Android Kotlin, en kiosque            │  WiFi      │ Node 22 + Fastify, port 3000                          │
│ MainActivity + un Fragment par mode         │ ─HTTP────▶ │ server.ts : jeton ; routes/ : routes par domaine      │
│ BackendClient (HttpURLConnection)           │  + jeton   │ deck.ts → os.ts ─┬─ mac/ (osascript, JXA)             │
│ RemoteChannel (long-polling) ◀──────────────│─ ordres ── │ tablet.ts (file   └─ win/ (MateHelper.exe, C#)      │
│ Discovery (UDP) ◀──────── diffusion ────────│─ UDP ───── │   d'ordres)        calendar, tasks, events, camera…   │
└─────────────────────────────────────────────┘            │ .data/ : données de cet ordinateur                   │
        │ MET Norway (météo, sans clé)                     └───────────────────────────────────────────────────────┘
        ▼                                                     ▲ mcp.ts (Claude Code / Desktop) relaie vers /tablet/command
```

Pas de serveur dans le cloud : chaque ordinateur a son compagnon, la tablette parle directement à celui qu'elle pilote. Seules les mises à jour passent par Internet : la tablette les lit dans les releases GitHub du projet (le compagnon peut aussi servir les siennes). Pas d'IA : l'Assistant IA a été retiré le 26/10/2026.

## Les deux programmes

### La tablette (`app/`)

- **Une seule Activity** (`MainActivity`) plein écran, barre fixe à gauche (Parler, profils Accueil / Deck / Réunion pendant un appel, outils, ordinateur, Réglages ; heure, WiFi, batterie et lecture en cours en haut à droite), un **Fragment par mode** : Profils (ex-Accueil), Deck, Depuis l'ordi, Focus, Caméra, Réglages. Les fragments sont créés une fois et cachés/montrés ; ils sont recréés quand on change d'ordinateur (`onComputerChanged`).
- **Panneau document** (`DocumentPanel`) à droite : document du dossier partagé ou page web de l'ordinateur, à côté de n'importe quel mode ou en grand.
- **Kiosque** : l'appli est *device owner* (installée sur une tablette réinitialisée, voir [kiosque.md](kiosque.md)). Elle verrouille l'écran sur elle-même (lock task), masque l'agent de provisionnement du constructeur, bloque les installations et adb (réouvrables par le technicien), s'installe elle-même ses mises à jour et règle le WiFi.
- Vues XML, pas de Compose ; dépendances : appcompat, lifecycle, coroutines. HTTP par `HttpURLConnection` + `org.json`. Tout doit rester léger (MT8167, 2 Go de RAM).

### Le compagnon de l'ordinateur (`backend/`)

- **Node 22, TypeScript lancé par `tsx`** (pas de compilation), **Fastify**. Appli portable, sans installation : l'exe Windows (`src/win/Mate.exe` + zip du runtime) ou `Mate.app` extrait son runtime dans le dossier de l'utilisateur, lance le serveur et le relance s'il s'arrête (sortie 75 = quitter, 76 = tout oublier). Le lancement à l'ouverture de session est une case du panneau (`src/portable.ts` : clé Run sous Windows, LaunchAgent sous Mac), rien n'est inscrit avant. Depuis le dépôt : `scripts/service.ts`.
- **`server.ts`** vérifie le jeton `Authorization: Bearer`, traduit les erreurs, enregistre les routes et lance les tâches de fond. Les routes (contrat de l'API) sont dans **`routes/`**, un plugin Fastify par domaine (`pairing.ts` pour `/health` et `/pair/*`, `local.ts`, `portable.ts` (carte « Cette appli » du panneau), `deck.ts`, `windows.ts`, `system.ts`, `docs.ts`, `browser.ts`, `camera.ts`, `calendar.ts`, `tasks.ts`, `calls.ts`, `tablet.ts`, `updates.ts`) ; les hooks posés dans `server.ts` valent pour tous. Sans jeton : `/health`, `/pair/*`, la page locale `GET /` (seulement depuis l'ordinateur).
- **`os.ts`** est le seul point d'entrée vers le système : il appelle `mac/` ou `win/` selon l'OS. Ajouter une action système = l'écrire dans les deux.
  - **Mac** (`src/mac/`) : `osascript` en AppleScript ou JXA. Frappes en CGEvent (System Events refuse les saisies), fenêtres par l'Accessibilité + NSScreen + CoreGraphics. Demande l'autorisation Accessibilité.
  - **Windows** (`src/win/`) : un **programme résident `MateHelper.exe`** (C# .NET Framework 4.8, compilé d'avance : `helper/Native*.cs` pour fenêtres, son, frappes, une classe partielle découpée par thème ; `helper/Program.cs` pour l'UI Automation ; `helper/Media.cs` pour les contrôles multimédias WinRT). `helper.ts` lui envoie des commandes JSON ligne par ligne. L'exe est copié dans `%LOCALAPPDATA%\Mate\helper` avant lancement pour ne pas verrouiller l'original. Pas de PowerShell : un script qui compile du C# de frappes à la volée était classé malveillant par Bitdefender.
- **`.data/`** (non versionné) : tout ce qui est propre à cet ordinateur (voir « Où sont les données »).

## Les flux principaux

### 1. Appairage et découverte

1. Le compagnon crée au premier lancement son identité et son jeton (`.data/identity.json`) et répond à une diffusion UDP sur le WiFi (`pairing.ts`).
2. La tablette n'affiche aucune liste : elle prend l'ordinateur qui « attend une tablette », c'est-à-dire dont la page locale est au premier plan (la page envoie `POST /local/visible {visible}` à chaque rafraîchissement tant qu'elle est visible, une fois quand elle se cache ; `pairing.ts` : `notePageVisible`, `waiting`, valable 5 s ; la réponse UDP porte `waiting` et `waitingMs`). `net/Discovery.pickToPair` garde, parmi eux, celui dont la page est ouverte depuis le moins longtemps ; `ui/PairingSession.kt` (`AutoPairing`, recherche toutes les 4 s) lance l'appairage. L'attente du code est bornée par `expiresInMs` de `/pair/reveal` (au plus 2 min), puis « Code expiré ». Après un échec (expiration, trois codes faux, connexion perdue) la tablette n'insiste pas : l'ordinateur reste écarté (`Discovery.stillBlocked`) jusqu'à un toucher sur le message (« Toucher ici pour recommencer ») ou un changement de sa page (cachée puis rouverte). Un ordinateur qui répond sans HTTPS (ancien compagnon) est signalé à l'écran (`outdatedAmong`). « Saisir son adresse » reste en secours ; l'ordinateur qui n'attend pas ouvre alors sa page lui-même, en plus de la notification.
3. En WiFi, tout passe en HTTPS (certificat auto-signé de l'ordinateur, `tls.ts`) ; le HTTP n'écoute que sur 127.0.0.1. La tablette affiche un code à 6 chiffres, qui mêle l'empreinte du certificat qu'elle voit ; l'utilisateur le saisit dans la page de Mate de l'ordinateur (`http://127.0.0.1:3000/`), prévenu par une notification système (`os.notify` : centre de notifications du Mac par `osascript display notification`, bulle de la zone de notification de Windows par le helper ; sur le Mac la notification s'affiche au nom d'« Éditeur de script » (titre « Mate », icône d'Éditeur de script, vérifié par capture le 04/11/2026) : l'agent Mate n'est pas une appli qui peut en poster, et si l'utilisateur coupe les notifications d'Éditeur de script elle n'apparaît pas, le code reste alors à saisir dans la page ouverte), la tablette reçoit le jeton et épingle le certificat. Détails et protocole : [securite-appairage.md](securite-appairage.md).
4. La tablette garde une **liste d'ordinateurs** (`Computers.kt` : id, nom, url, jeton, os, empreinte épinglée) et pilote l'actif. Si l'actif ne répond plus, `net/Connection.kt` retrouve sa nouvelle adresse par la recherche, ou bascule vers un autre ordinateur qui répond.
5. **Plugins** (première utilisation) : le compagnon propose ses plugins (`plugins.ts`, `GET /plugins`) : applis trouvées sur l'ordinateur (Discord, Teams, Claude Code) et fonctions intégrées (Ouvertes, Son, Pavé, Média). La tablette ouvre l'écran des plugins (`PluginsView`) tant qu'un plugin n'a jamais été proposé : au premier appairage, et quand une appli compatible apparaît ensuite. Les choix (`POST /plugins`, `.data/plugins.json`) valent pour cet ordinateur. Un plugin coupé : sa page disparaît du deck (`/deck`), ses appels ne sonnent plus, ses onglets sont masqués (`off` de `/deck/features`). Jamais choisi = actif. Rouvrable dans Réglages > Plugins.

### 2. Une requête ordinaire (tablette → ordinateur)

`BackendClient` envoie du JSON avec le jeton ; les erreurs sont traduites en phrase par `errorText(e)` (`ui/Errors.kt`), jamais affichées brutes. Côté compagnon, `setErrorHandler` remplace les erreurs techniques par une phrase en français.

### 3. Les ordres de l'ordinateur vers la tablette (canal `/tablet`)

La tablette n'ouvre aucun port. `remote/RemoteChannel.kt` garde une requête `POST /tablet/poll` ouverte (long-polling) ; le compagnon y dépose les ordres (`tablet.ts`) : rappel parlé d'une tâche ou d'un événement, message, changement de mode, capture d'écran, sonnerie pour retrouver la tablette (ordre `ring`, `audio/Ringer.kt` : son d'alarme au maximum en boucle, volume remis ensuite ; un toucher, l'ordre inverse ou 2 minutes l'arrêtent ; bouton « Faire sonner » du panneau Tablette et outil `tablette_sonner`), page web en plein écran par-dessus tout (ordre `page`, `ui/PageOverlay.kt`, http(s) seulement, bouton Fermer ; voir § Maquettes sur la tablette)… Livraison « au moins une fois », dédoublonnée par la tablette. C'est aussi par là que passe **l'extension Claude** (`mcp.ts`, serveur MCP qui relaie vers `POST /tablet/command`). Si l'écran de la tablette est éteint, l'appli est en pause et les ordres attendent.

### 4. Le Deck

- Les touches sont définies **uniquement côté ordinateur** : `config/deck.json` (départ copié de `deck.example.json` ou `deck.example.windows.json`, filtré aux applis installées), touches perso (`.data/keys.json`, `perso.ts`), applis ajoutées (`.data/apps.json`), sites de la page Média (`.data/links.json`).
- La tablette reçoit les pages (`GET /deck`) et n'envoie qu'un **identifiant de touche** ; `runAction` (`deck.ts`) exécute les étapes (app, keys, text, url, media, system, wait, gesture, http, window, macro, cycle). Aucune commande arbitraire ne vient de la tablette.
- **Étape `http`** (`backend/src/lan-call.ts`, schéma dans `perso.ts`, outil MCP `deck_touche_affecter`, éditeur de la page locale) : une touche appelle une cible du réseau local (prise, lampe, NAS). Les cibles sont déclarées dans `LAN_TARGETS` du `.env` de l'ordinateur (JSON : nom → `url`, `method` GET/POST/PUT, `token` facultatif) ; l'étape ne porte que le **nom** de la cible (une adresse ajoutée est retirée par la validation), la tablette ne voit ni adresse ni jeton. Garde propre à `lan-call.ts`, à part de `net-guard.ts` (qui interdit le réseau local aux icônes) : liste d'autorisation exacte (10/8, 172.16/12, 192.168/16, 127/8, fc00::/7, fe80::/10 ; une IPv4 mappée en IPv6 est jugée comme IPv4), appliquée par l'option `lookup` de `node:http(s)` : le nom est résolu une fois et la connexion part vers l'adresse vérifiée (pas de rebinding DNS), le nom restant dans Host et SNI ; 403 sinon. Une cible qui vise le port du compagnon sur cet ordinateur est ignorée au démarrage, un seul appel à la fois par cible (un second appui rejoint l'appel en cours), redirections non suivies, un jeton demande https (sinon la cible est ignorée au démarrage), délai 8 s, réponse jamais relayée, `NODE_USE_ENV_PROXY` à ne pas activer. `POST /deck/run` rend `{ ok, http: { name, status } }` ; cible inconnue 404, refus de l'appareil (hors 2xx) ou pas de réponse 502 avec une phrase (`message`, lue par la tablette comme les autres erreurs). Pas encore : éditeur de l'étape sur la tablette (KeyEditor), affichage du succès sur la touche, corps de requête, certificats auto-signés.
- **Étape `output` (Sortie son)** (`runAction` de `deck.ts`, schéma dans `perso.ts`, outil MCP `deck_touche_affecter`) : `{ id, name }`, l'id d'une sortie de `audioOutputs` (UID Core Audio sur Mac, id d'endpoint `{0.0.0.00000000}.{guid}` sur Windows, stables) et son nom pour l'affichage. À l'appui, l'id doit être dans la liste de l'ordinateur (comme `POST /system/audio/output`), sinon 404 « Sortie son introuvable : <nom> » (casque débranché), rien n'est changé ; puis `setAudioOutput`. Avec « Une étape à chaque appui » (`cycle`), deux étapes = casque puis enceintes ; comme pour toute étape d'un cycle, une sortie absente garde la touche sur cette étape (l'appui suivant la retente). Éditeur de la tablette : pastille « Sortie son » de `KeyEditor`, liste relue à chaque ouverture (`outputStep` de `KeyJson.kt`). `deck_touches_lister` donne `sorties_son` (vide si l'ordinateur ne pilote pas le son). La page locale garde l'étape telle quelle sans la proposer (choix depuis la tablette). Hors périmètre : micro (entrée son).
- **Seconde action (appui long)** : une touche de `config/deck.json` peut porter `hold` (une action, comme `action`). `GET /deck` donne `hold: true` ; `POST /deck/run` avec `hold: true` lance cette action (409 sans `hold`). Dans le widget Touches, l'appui long d'une touche qui en a une la lance ; sans elle, il propose de la retirer du widget. Une touche perso (`keys.json`) porte `hold` : une liste d'étapes (une = raccourci simple, plusieurs = macro), réglée dans l'éditeur par la pastille « Seconde action (appui long) ». L'éditeur d'une touche s'ouvre seulement en mode Modifier (réglages du widget Touches, bouton « Modifier » en face d'une touche perso), plus à l'appui long ; « Nouvelle touche » ouvre toujours l'éditeur. **Touche à maintenir (parler en maintenant)** : une étape `keys` avec `push: true`, seule dans sa touche (ni cycle, ni seconde action : 400 à l'enregistrement), réglée dans l'éditeur par la pastille « Maintenir pour parler » de l'étape Raccourci clavier. `GET /deck` donne `push: true` ; la tablette envoie `POST /deck/run` avec `phase: "down"` au doigt posé et `phase: "up"` au doigt levé (ou annulé, ou widget retiré), dans l'ordre ; `holdTile` (`deck.ts`) tient puis lâche les touches par `os.holdKeys` (Mac : événements `CGEventPost` en deux appels, Windows : op `holdkeys` du pilote), et les lâche seul après 60 s sans relâchement ou à l'arrêt du compagnon (appels d'une même touche mis en file, relâchement d'une touche non tenue sans effet, combinaison relâchée = celle qui a été tenue). La tablette envoie le relâchement hors du scope de la vue (réessayé 2 fois) ; une telle touche n'a pas d'appui long dans le widget, elle se retire par ses réglages. Un appui simple (sans `phase`) refuse (409) : le micro resterait ouvert. F13 à F20 sont acceptées (touches que rien d'autre n'utilise). Seul le widget Touches la gère. L'outil MCP `deck_touche` et la page locale ne règlent pas `hold` (la page locale le garde tel quel à l'enregistrement).
- **Sauvegarde de la configuration** (1/11/2026, issue #62, page locale, section Sauvegarde ; vu en test backend et e2e, pas sur la tablette) : `GET /local/config/backup` rend un fichier `mate-config-1` (touches Perso, pages de touches, applis, sites, plugins, et profils, widgets et barres lus sur la tablette au dernier passage), `POST` reprend les parties cochées en revalidant par les schémas des routes de la tablette. Page locale seulement : un hook de la route refuse en 403 toute requête dont l'IP n'est pas loopback ou dont l'hôte n'est pas local, même avec le jeton. Tout est vérifié avant la première écriture (tout ou rien) : noms d'étape `app` et `shortcut` sans `/`, `\` ni `.app` (400), sites passés par `normalizeLink` (`deck.ts`, comme l'ajout depuis la tablette) puis dédoublonnés, disposition bornée (20 profils, 200 widgets, champs de widget connus). Sur la page, le choix d'un fichier affiche l'aperçu des touches (libellé et étapes, en texte seul) et « Reprendre » attend la case « J'ai relu ces touches » dès qu'une étape `app`, `text` ou `keys` est cochée ; l'avertissement rappelle que le fichier contient texte, adresses, notes et listes. Jamais `identity.json`, `agents-hook.json`, `accounts.json`, `github.json`, `gitlab.json` ni l'agenda, les tâches ou le mixage. Les profils repartent par l'ordre `layout` `set` : tablette éteinte, cette partie attend (`skipped`), le reste est repris. Code : `src/backup.ts`, `src/routes/local-backup.ts`, `src/local-config-backup.ts`. Pas de bouton sur la tablette.
- **Enregistrer une macro sur le Pavé** (#80) : le widget Pavé a un bouton « Enregistrer » ; jusqu'à « Terminer (n) », chaque geste fait (les 12 de `POINTER_GESTURES`, déjà envoyés à l'ordinateur) est noté par `ui/pointer/MacroRecorder` avec la pause réelle avant lui (arrondie à 100 ms, ignorée sous 200 ms, plafonnée à 10 s, étape `wait`). Terminer envoie la touche « Macro du Pavé » par `POST /deck/keys` (`addKey` de `perso.ts` : première place libre de Perso, 409 si pleine, rend `{ slot }`) ; modifiable ensuite dans l'éditeur. L'étape `gesture` (`{ name }`, `runAction` → `pointerGesture` : le raccourci du système, comme le Pavé) est valide dans toute touche perso, l'outil MCP `deck_touche` et la page locale. Shortcut : seuls les gestes sont gardés (ni déplacements, ni clics, ni frappes) ; 20 étapes au plus par touche (le 11e geste avec pauses est refusé) ; un enregistrement ne survit pas à un changement d'écran ; pas d'enregistrement vers une page nommée.
- **Pavé tactile dans les 16 formes** (#183) : en Bloc, Grand et Plein écran, le pavé entier (`PadView`, un seul par widget, il garde l'enregistrement) ; en Pastille, Ligne et Colonne, `PadCompact` : Pastille = un bouton Clic (toucher = clic gauche, maintenir = clic droit) ; Ligne et Colonne (variante B) = une bande de défilement sur un axe (`ui/pointer/ScrollStrip.kt` : un doigt, même pas et même sens que le défilement à deux doigts, une tape ne fait rien) qui prend deux tiers de la place, et le bouton Clic au bout. Canal `PointerChannel` ouvert seulement page à l'écran. Aperçu du catalogue (`PadSample`) : le pavé ou ses boutons sans canal, même sans Mac ni Windows.
- **Dupliquer une touche ou une page** : `POST /deck/keys/duplicate` (`{ slot, page?, to? }`, `page` et `to` absents = Perso) copie une touche enregistrée dans la première place libre de la page `to` (la copie est indépendante ; 404 touche vide ou page inconnue, 409 page pleine) et rend où elle est (`{ page?, slot }`) ; `POST /deck/pages/:page/duplicate` ajoute à la fin une copie de la page nommée, titrée « … (copie) » (404 inconnue, 409 au-delà de 50 pages), et rend son rang. Mêmes routes sous `/local/config/` pour la page locale. `duplicateKey` et `duplicateKeyPage` sont dans `perso.ts`. Sur la tablette, l'éditeur d'une touche enregistrée a un bouton « Dupliquer » : il liste Perso et les pages nommées (`duplicateTargets`), un choix copie et ferme l'éditeur. La page locale a « Dupliquer la page » sur chaque page nommée. Pas d'outil MCP, ni de création, renommage ou suppression de page.
- **Touche large** : une touche enregistrée (`PersoKey.span`, `1 | 2`) peut occuper deux cases de large ; `keySchema` n'accepte que 1 ou 2, `GET /deck` donne `span: 2` sur la tuile (absent pour une touche simple) et la page web locale garde le `span` à l'enregistrement. Sur la tablette, l'éditeur a la pastille « Touche large » (`keyJson(span = 2)`) ; `KeyRef.span` et `DeckTile.span` suivent. `TileGridView` (grille des widgets, dont Touches en L et XL) reste un `GridView` : la touche large reçoit la largeur de deux colonnes et une case vide couvre la seconde ; `spanSlots` (`TileLogic.kt`) place les cases, une case vide devance une touche large qui tomberait en dernière colonne, et sur une colonne tout est simple. Hors de la grille, Touches et Applis (#183) n'élargissent pas une touche large : en Pastille, Ligne et Colonne, ils montrent les premières touches sans défiler (`TileStrip`, `ui/home/TileStrip.kt`) : Colonne = une liste icône et nom, Ligne = des icônes seules, autant que la largeur en tient, Pastille = l'icône de la première ; le nombre suit la taille réelle de la vue. Bloc, Grand et Plein écran gardent la grille qui défile et son « + ».
- Onglets : pages fixes, puis pages d'appli (Discord, Réunion) tant que l'appli tourne ou est en appel (`GET /deck/live`). On change d'onglet en touchant ou en balayant la grille.
- **Ouvertes** : toutes les fenêtres de l'ordinateur sur le schéma de ses écrans (`OpenWindowsView` + `ScreenMap`, `GET/POST /windows/open`), relu toutes les 5 s.
  Widget de l'Accueil (`WidgetType.OPEN`, 16 formes, #183) : cette vue en Bloc, Grand et Plein écran ; en Pastille, Ligne et Colonne, un résumé sans glisser (`OpenWindowsCompact`, logique pure `OpenWindowsSummary`) : l'icône de l'appli au premier plan et le nombre de fenêtres, les icônes des applis (un trait sous celle du premier plan), ou leur liste ; toucher une appli met sa fenêtre devant (`focus`), l'appui long revient à la grille. Aperçu du catalogue : `OpenWindowsSample`, sans réseau (`OpenWindowsView.showSample` ne charge ni icône ni liste).
  Thèmes Instrument (« A · Patch de régie », #243 ; drapeau `instrument` posé par le widget, jamais par le Deck) : chaque écran a un LCD « ÉCRAN 1 · PRINCIPAL » et ses fenêtres en capuchons à DEL numérotés (`CapGrid`, `WindowCapViews` sur `item_key_cap`, DEL = premier plan), la corbeille est une longue touche (`TrashZone`, DEL `c_signal` au survol) ; petites formes : un capuchon par appli (« CHROME · 2 »). Logique pure : `WindowCaps` (`appLabel`, `screenTitle`, `columns`).
- **Média** (Windows et Mac) : lecture en cours lue dans les contrôles multimédias de Windows (`/system/media`) ou, sur Mac, par MediaRemote (« À l'écoute », `src/mac/media.ts` + `NowPlaying.dylib` chargée par `/usr/bin/perl`, seul accès possible depuis macOS 15.4 : risque qu'Apple le ferme, secours par les titres d'onglets) ; musique ouverte dans l'appli du site si elle est installée, sinon le site (`music.ts`). Sur Mac, les commandes passent par l'extension du navigateur qui joue quand elle est chargée (dans la page : lecteur, actions Media Session), sinon par MediaRemote.
- **YouTube Music** (branche `Version-Gen2`, côté ordinateur seulement pour l'instant) : l'onglet tourne dans le navigateur de l'ordinateur, la tablette le pilote. `extension/ytmusic.js` (script de contenu de music.youtube.com) relève chaque seconde le titre joué, la pochette, la position, « J'aime », la répétition, la file d'attente et les résultats de recherche, et les pousse à chaque changement (et toutes les 5 s) par `background.js` à `POST /browser/extension/ytmusic` (local, origine d'extension exigée). `src/ytmusic.ts` garde le dernier état par navigateur 30 s (textes coupés, pochettes Google seulement, en 544 px) ; `GET /ytmusic` le rend à la tablette (`open: false` sans onglet). `POST /ytmusic/action` n'accepte que la liste fermée `YT_MUSIC_OPS` (lecture, suivant, précédent, position, j'aime, je n'aime pas, aléatoire, répétition, titre de la file, recherche, résultat), relayée par le long-polling de l'extension (`action: "ytmusic"`) ; sans onglet, seule la recherche part (l'extension ouvre YouTube Music sur les résultats), le reste répond 409. **Appli de bureau YTMDesktop 2** (`src/ytmdesktop.ts`), prioritaire sur l'onglet quand elle est connectée et répond : son Companion Server (`http://127.0.0.1:9863/api/v1`, `YTMD_URL` pour les tests ; YTMDesktop > Réglages > Integrations : « Companion server » et, le temps de connecter, « Enable companion authorization ») ; `POST /ytmusic/desktop/connect` demande un code à 4 chiffres (affiché sur la tablette et dans YTMDesktop), l'accord se donne dans YTMDesktop, le jeton reste dans `.data/ytmdesktop.json` (600) ; Pastilles File d'attente / Paroles (XL, L3) : `GET /ytmusic/lyrics` (`src/lyrics.ts`) cherche les paroles du titre en cours dans LRCLIB (lrclib.net, sans clé ; `LYRICS_URL` pour les tests) : exacte avec puis sans l'album, puis avec l'artiste principal seul (`mainArtist`), puis recherche libre à ±3 s de durée ; 503 réessayé une fois, un essai en erreur n'arrête pas les suivants ; trouvé ou « rien » (seulement si tout a répondu) gardé en mémoire (200 titres) ; LRC lu en lignes horodatées (`parseLrc`). Bouton « Ouvrir sur l'ordi » : `POST /ytmusic/open` lance ou met devant YTMDesktop (relié ou installé), sinon ouvre le site.

### 5. Agenda, tâches, rappels

- Agenda (`calendar.ts`) = liens ICS (`.data/calendar.json`) + comptes Microsoft/Google (`accounts.ts`, OAuth, pas encore activé : identifiant d'appli à obtenir) + agenda personnel noté depuis la tablette (`events.ts`). Réunions en ligne détectées dans les événements (`meeting-links.ts`), ouvertes sur l'ordinateur par `POST /calendar/join`.
- Tâches (`tasks.ts`) : corvées à tour de rôle (récurrente avec `people`, dans `config/tasks.json` ou par `POST /tasks` ; cocher passe à la personne suivante, décocher revient, compteur `turns` dans `.data/tasks.json` ; la carte affiche « Tour de X » ; pas de saisie dans la fenêtre ⏰ ni dans l'outil MCP), ponctuelles, récurrentes (créées depuis la tablette), ou quotidiennes écrites dans `config/tasks.json` (exemple : saisir son temps dans Jira, cochée seule via `jira.ts`). Les rappels partent de l'ordinateur par le canal `/tablet` et sont lus à voix haute par la tablette (`audio/Speaker`).
- Onglet Jira du Deck (`routes/jira.ts`, tablette `ui/JiraView`, `net/JiraApi`) : tickets assignés en colonnes : l'union des colonnes des tableaux Jira choisis sur la tablette (API Agile, `GET/POST /jira/boards`, choix dans `.data/jira.json`), colonnes réunies par nom entier ou synonyme exact (« Ready for Dev » et « Ready for QA » restent deux colonnes), ⚙ du widget : colonnes masquées et « tous les tickets » par colonne (`GET/POST /jira/columns`), terminés des 7 derniers jours compris, ticket placé par l'id de son statut ; sans tableau choisi, une colonne par statut (à faire puis en cours). Toucher un ticket = ses transitions Jira ; une transition qui demande un champ (`needsJira`, ou Jira répond 400 → 409) se finit dans Jira, ouvert sur l'ordinateur. Proposé seulement si Jira est configuré (`/deck/features` → `jira`).
- Eau et Focus (Pomodoro, ambiance) sont **sur la tablette seulement** (`focus/`).

### 6. Visualiseur (mode Caméra)

`camera/DocCamera.kt` (Camera2) envoie du JPEG 720p à ~10 i/s à `POST /camera/frame` ; le compagnon garde la dernière image et la sert en MJPEG sur `http://127.0.0.1:3000/camera`, à projeter. « Envoyer une photo » : photo pleine taille dans le dossier Partage.

### 7. Cadre photo

Après quelques minutes sans toucher (Depuis l'ordi > Cadre photo, `ui/FrameSettingsView` : 2, 5, 10 ou 30 min, ou jamais ; vignettes, Ouvrir le dossier sur l'ordi, Essayer), les photos du dossier « Cadre photo » du dossier partagé défilent en plein écran, l'heure et la date en bas (`ui/PhotoFrameView`, lancé par `MainActivity.followFrame` à chaque minute) ; un toucher revient à l'écran sans agir dessous. `GET /frame` (`docs.ts`) liste les images (JPEG, PNG, WebP, sous-dossiers compris, 500 au plus) ; `frame/FrameCache` les copie une fois par `/docs/file`, réduites à la taille de l'écran et remises droites (EXIF), un dossier par ordinateur : le cadre marche ordinateur éteint. Économie (`frame/FrameLogic`) : luminosité plafonnée à 35 % (20 % sur batterie), image fixe entre deux fondus de 600 ms, écrans dessous masqués, arrêt la nuit (atténuation) et sous 20 % de batterie débranchée ; pas de cadre pendant un appel, une question d'agent, le Focus qui tourne, la Caméra ou un document ouvert.

### Partager vers Mate

Depuis la Galerie, un navigateur ou un gestionnaire de fichiers, « Partager » puis « Mate » dépose les fichiers (PDF, image…) ou le lien dans le dossier partagé de l'ordinateur actif. `share/ShareActivity` (filtres `SEND` et `SEND_MULTIPLE`, fenêtre transparente `Theme.Companion.Share`, hors des récents) copie chaque fichier dans un sous-dossier de cache propre au lancement, sous son nom (`share/ShareLogic` : seulement des URI `content://` d'une autre appli, jamais `file://` ni une autorité `app.mate…` ; 10 fichiers au plus, le surplus refusé avec un message ; nom nettoyé, lien rangé dans `Lien <date>.txt` ; copie bornée à 20 Mo : elle s'arrête à 20 Mo + 1 octet sans lire la fin du flux) et l'envoie par `DocsApi.share` à `POST /docs/share` (`routes/docs.ts`, `saveShared` de `docs.ts`) : le fichier arrive à la racine du dossier partagé, jamais par-dessus un fichier déjà là (`nom (2).pdf`) ; extensions en liste blanche (pdf, images, texte, Office, OpenDocument, zip, audio, vidéo : voir `SHARE_EXTENSIONS`), le reste refusé en 415 ; nom sans caractère de direction ni invisible, nom réservé Windows testé avant le premier point (`con.x.txt` → `_con.x.txt`) ; plus de 20 Mo : 413, rien n'est déposé. ### 7. Commande vocale (bouton Parler)

Pas d'IA : la reconnaissance est celle d'Android (`SpeechRecognizer`, servie par l'appli Google de l'image d'usine : en ligne, sans clé ni compte ; à ne pas désactiver dans la procédure de kiosque). Les noms d'applis mal entendus sont rapprochés à l'oreille (prononciation approximative + distance d'édition, sur les 5 variantes du reconnaisseur : « en cabane launcher » → Ankama Launcher). `voice/VoiceControl.kt` écoute et exécute ; appui long = commande écrite (émulateur sans reconnaissance). ### 9. Mises à jour de la tablette

Deux sources, même format (`{"updates":[{package, label, versionCode, versionName, file, size, sha256}]}`) :

- **L'ordinateur relié** (serveur simulé par le backend, `updates.ts` : `.data/updates/manifest.json` + APK), avec le jeton d'appairage. Il sert aussi le WebView.
- **GitHub** : assets de la release `latest` du dépôt public `BuildConfig.UPDATE_REPO` (`manifest.json` puis chaque fichier), lus par leurs liens de téléchargement publics (`net/GitHubReleases.kt`), sans API ni jeton. Marche sans ordinateur. Manifeste absent (404) : « aucune mise à jour », pas d'erreur ; tout autre refus (limite, panne, réseau) s'affiche avec sa phrase (`GitHubException.textRes`), et l'échec d'une installation sous la ligne concernée. `-PupdateUrl=` remplace GitHub par un serveur HTTP simple (essai local).

`kiosk/Updater.kt` interroge les deux en parallèle et fusionne (`kiosk/UpdatePlan.kt` : par paquet, la plus haute `versionCode` ; à égalité, l'ordinateur). Il télécharge, vérifie le SHA-256 et installe en silence (device owner), une installation à la fois ; hors kiosque (#143, Mate en appli ordinaire, à côté d'UnoMate par exemple), Android répond « confirmation demandée » : Mate ouvre son écran (qui propose aussi « Sources inconnues » la première fois) et attend la réponse (10 min de plus pour répondre), refusée = « Installation refusée sur la tablette » ; Mate pas à l'écran (Android 10 bloquerait cet écran en silence, `kiosk/InstallStep`) ou sans réponse : l'installation est abandonnée et le message dit d'ouvrir Mate. Essai plus ancien à désinstaller d'abord : « Annuler » reste possible jusqu'à la confirmation de la désinstallation. Le bouton « Mettre à jour » de la page de l'ordinateur marche aussi hors kiosque (`RemoteUpdate`, clé `confirm` de l'état : la page dit de confirmer sur la tablette) ; seule l'appli d'essai le refuse. `kiosk/AutoUpdater.kt` vérifie au démarrage puis toutes les 6 h (échéance relue tous les quarts d'heure) et installe seul la release `latest` la plus récente du Mate (jamais un essai), en device owner seulement, sans rien afficher (hors kiosque, personne ne confirmerait). La carte Mises à jour de Réglages montre les deux sources (une version plus basse que l'installée est marquée non installable, Android la refuserait ; une ligne par source en erreur) puis, dessous, les essais de PR (voir plus bas). `kiosk/UpdatedReceiver` relance l'appli en kiosque après sa propre mise à jour.

**Essai d'une PR** (`trial/`) : une version `X.Y.Z-essai.N` est une autre appli, `app.mate.essai` « Mate essai » (`applicationIdSuffix`, `BuildConfig.TRIAL`, `app/build.gradle.kts`), signée par la même clé et installée à côté de la stable. La stable reste device owner. Les essais de toutes les PR sont publiés dans la release `essais`, un manifest `{"essais":[…]}` à une entrée par PR (`net/UpdatesApi.essais()` : même dépôt et même jeton de lecture, tag `essais`, sans passer par l'ordinateur ; `Updater.essais`, source `UpdateSource.TRIALS`). Réglages > Mises à jour les liste (« #109 titre », version, backend remplacé ou non), en mode technicien seulement : appui long sur le titre des Réglages + code technicien, jusqu'à la sortie des Réglages, même état que la carte Kiosque ; sans lui, ni liste, ni requête à la release `essais`, ni « Ouvrir l'essai », mais « Revenir à la stable » reste visible (`EssaiPlan.showList`/`showSwitch`) ; choisir une PR installe son essai à la place du précédent (`AutoUpdater` ne prend que son propre paquet), en le désinstallant d'abord, sans confirmation, si sa `versionCode` est plus basse (`EssaiPlan.install`, `Updater.uninstall`), puis met le backend de l'ordinateur actif sur celui de la PR (`EssaiBackend.sync`). La stable autorise l'essai en lock task (`setLockTaskPackages`), lui accorde micro et caméra, et l'ouvre (« Ouvrir l'essai » : relit le backend de la PR installée, `Prefs.trialMr`, et le remet si l'ordinateur n'y est plus). L'essai, jamais device owner, se verrouille seul si la stable l'y autorise (`isLockTaskPermitted`) et rend la main par « Revenir à la stable » (il restaure le backend d'origine de l'ordinateur, puis se ferme ; la stable, à son retour, le refait si l'essai a planté : `Prefs.trialOpened`). Au premier lancement, il reprend la liste des ordinateurs de la stable, jetons compris, sans réappairer : `trial/ComputersProvider` de la stable, exporté sous la permission `app.mate.permission.COMPUTERS` de niveau signature (Android refuse toute appli d'une autre clé) ; ensuite chacune garde sa liste. Une seule des deux tourne au premier plan : le canal `/tablet` ne vit que pendant `STARTED`, pas de conflit sur l'ordinateur.

**Backend d'une PR sur l'ordinateur** (`backend/src/essai-backend.ts`, routes dans `routes/updates.ts`) : la tablette télécharge dans la release `essais` l'archive de la plateforme de l'ordinateur (`backend-<version>-mac|windows.tar.gz`, backend sans node ni lanceur Windows, fabriqué par `npm run package -- essai`), vérifie taille et SHA-256, et l'envoie (`POST /companion/backend/essai?mr=&sha256=`, jeton d'appairage : aucun secret ne va à l'ordinateur). L'ordinateur extrait à part, vérifie, garde une seule copie de son backend installé (`<données>/backend-origin`, jamais écrasée par un essai suivant), remplace `dist/`, `src/`, `scripts/`, `assets/` et les fichiers livrés de `config/` (pas `node/`, le lanceur, `.env`, `deck.json`, `tasks.json`), écrit `essai-backend.json` et redémarre. `GET /companion/backend` donne l'état, `POST /companion/backend/origin` restaure. Compagnon lancé depuis le dépôt : 409, l'essai du backend marche seulement avec le paquet. Détails : `docs/developpement.md`, « Déployer un essai depuis une PR ».

### 10. Agents Claude (Mac)

La tablette montre les sessions Claude Code de l'ordinateur (qui travaille, qui a fini, qui attend) et y répond. `agents.ts` tient l'état par `session_id`, en mémoire, de trois sources : `claude agents --json` (toutes les 4 s, seulement tablette connectée : le filet), les hooks HTTP de Claude Code (`POST /agents/hook`, local, secret propre dans `.data/agents-hook.json`, posés par `npm run agents:hooks`) et `orca worktree ps --json` si Orca est là (branche, terminal). États : travaille, attend, fini, limite, inactif. La tablette est prévenue par l'ordre `agent` du canal `/tablet` (lumière de bord et son), sauf si l'appli de devant est un terminal ou Orca : l'utilisateur n'est alors pas prévenu. Répondre : le hook `PermissionRequest` (permission) ou `PreToolUse` sur `AskUserQuestion` (question à choix) reste ouvert jusqu'à `POST /agents/answer` ou `AGENTS_HOLD_S` (90 s), puis reçoit `{}` : le terminal décide. Sur la tablette, la carte de la demande (`AgentAskOverlay`) s'ouvre en touchant la lumière de bord ou une session de l'onglet : permission (Autoriser une fois / Refuser ; une commande à risque, `isRisky` côté compagnon, s'autorise en maintenant le bouton) ou questions à choix, une page par question, multi-choix, « Autre » écrit ou dicté. Sur une session au repos dans un terminal Orca (volet exact donné par `$ORCA_PANE_KEY` en en-tête du hook, terminal par `orca terminal list`), « continue » ou une phrase partent par `POST /agents/send` (`orca terminal send`) ; après une limite d'usage (`StopFailure` `rate_limit`), la tablette peut armer l'envoi de « continue » à l'heure de reprise lue dans le message. Les sessions de chat Orca et les terminaux ordinaires n'ont pas de moyen fiable : pas de bouton. Toucher une session l'amène devant : son terminal (`orca terminal switch`), sinon son chat Orca (worktree et onglet `agent-session:<id>` activés par le client du runtime d'Orca, la CLI ne sachant pas le faire), sinon Orca seulement. Par l'extension MCP, Claude lit lui-même l'état des autres sessions (`agents_lister`) et peut poser une question à choix sur la tablette (`tablette_demander`, `POST /agents/ask-tablet`) : même carte, réponse renvoyée comme résultat d'outil. Interrompre une session (Échap dans son terminal Orca, après confirmation) et usage Claude du compte 5 h / 7 j (lu dans Orca, `rateLimits.claude` de `accounts.list` ; à défaut, statusline enveloppée par `agents:hooks --statusline`, seul `rate_limits` est lu) complètent l'onglet. Jamais de décision sans action sur la tablette, ni « toujours autoriser ». Détails et essais : [recherche-agents-claude.md](recherche-agents-claude.md).

### 11. Verrou de la tablette

Deux verrous indépendants, écran plein dans sa propre fenêtre par-dessus tout (`ui/LockScreen`, logique `lock/LockLogic`), gardés dans les préférences (tenus hors ligne et après une relance) :

- **Ordinateur verrouillé** : le compagnon relit la session chaque seconde (`screen-lock.ts` ; Mac : `IOConsoleUsers` d'`ioreg`, `mac/lock.ts` ; Windows : op `locked` du helper, `WTSQuerySessionInformation`). Verrouillée, ou prise par un autre utilisateur : toute route à jeton répond 423 sauf `/tablet/poll|result`, le pavé UDP est ignoré, les ordres de contenu ne partent plus (rappels redonnés après), les demandes d'agents reviennent tout de suite au terminal. La tablette apprend l'état par l'ordre `lock` (ou un 423), l'annonce dans l'état de son poll (`locked`) ; le compagnon la corrige à chaque tour si elle ne montre pas le bon. Ordinateur injoignable : elle reste bloquée. Réglages > Notifs et verrou > « Bloquer la tablette quand l'ordinateur est verrouillé » (`Prefs.blockOnComputerLock`, activé par défaut) : coupé, pas d'écran plein (`LockLogic.kind`), la tablette reste utilisable ; elle garde et annonce l'état comme avant, la pastille de la barre dit « verrouillé » (« ! », `linkMark`) et une action refusée affiche « <nom> est verrouillé » (`errorText`, 423). Le compagnon ne change pas.
- **À la main** : cadenas du pied de la barre ; code à 4 chiffres (empreinte salée) choisi au premier verrouillage ou dans Réglages > Notifs et verrou ; 5 codes faux = 30 s d'attente. Le déverrouillage du Mac ne le lève pas.
- **Verrou renforcé** (option de Réglages > Notifs et verrou, coupée par défaut, exige un code) : si l'ordinateur verrouillé ne répond plus depuis 30 s (dernière réponse au canal gardée dans `Prefs.lastContact`, donc aussi après une relance de la boucle ou de l'appli ; `LockLogic.lockAway`, vu par `RemoteChannel` à chaque échec), il a peut-être été emporté : la tablette pose le verrou à la main (`LockScreen.lockAway`, texte « ne répond plus »). Le déverrouiller ailleurs ne la rouvre plus ; seul son code le fait.

Sortie de secours : appui long, puis code technicien (lève les deux ; un ordinateur joignable et verrouillé reprend la main au tour suivant). Instance de test (`COMPANION_HEADLESS`) : jamais verrouillée.

## Ajouter une fonction : les recettes

- **Nouvelle route** : la déclarer dans le plugin de son domaine sous `routes/` (avec son schéma ; nouveau plugin = `app.register` dans `server.ts`), l'appeler dans le client de son domaine (`net/*Api.kt`). Erreur pour l'utilisateur = `throw new Error("phrase en français")`.
- **Nouvelle action système** : l'ajouter à `os.ts`, l'écrire dans `mac/` **et** `win/` (C# 7.3 dans `win/helper/`, `Native.<thème>.cs` pour le pilotage, puis `npm run build:helper`).
- **Nouvelle étape de touche** : type dans `deck.ts` (`runAction`), et dans `KeyEditor` si elle se règle depuis la tablette.
- **Nouvel ordre vers la tablette** : type dans `tablet.ts` + schéma dans `routes/tablet.ts` + outil dans `mcp-tools.ts` + branche dans `RemoteChannel.execute`.
- **Nouveau widget d'Accueil (Profils)** : le déclarer dans `WidgetModel`, le construire dans `HomeWidgets` (ou un fichier dédié de `ui/home/`).
- **Nouveau texte** : `strings.xml`, en français, court (la tablette est lue de loin), « ordinateur » (« ordi » sur les boutons courts).

Les conventions transverses sont dans [CLAUDE.md](../CLAUDE.md), section « Conventions du code » ; les conventions détaillées (noms historiques `Mac*` = l'ordinateur, Mac ou Windows ; clavier ; dialogues ; pièges de l'UI) sont dans la section « Détail par fonction » ci-dessous, tenue à jour à chaque changement.

### Widgets : les 16 formes (#178)

- **Formes** : la grille de l'Accueil fait 4 × 4 cases ; `WidgetSize` (`ui/home/WidgetModel.kt`) a les 16 rectangles de 1 × 1 à 4 × 4. Les noms (`S`, `M`, `L`, `T`, `W`, `XL`, `V`, `L3`, `T3`, `XL3`, `FULL`, puis `M3` 3 × 1, `V3` 1 × 3, `V4` 1 × 4, `L23` 2 × 3, `L33` 3 × 3) sont enregistrés dans les dispositions : ne jamais en renommer un. La forme d'un ajout est la première de `WidgetType.sizes` ; une forme ajoutée va après elle.
- **Familles** (`ShapeFamily`, `WidgetSize.family`) : un widget dessine une mise en page par famille, pas une par forme. Pastille (`PILL`, 1 × 1 : un chiffre, une icône, un bouton) ; Ligne (`ROW`, 2 × 1, 3 × 1, 4 × 1) ; Colonne (`COLUMN`, 1 × 2, 1 × 3, 1 × 4) ; Bloc (`BLOCK`, 2 × 2, 3 × 2, 2 × 3, 3 × 3) ; Grand (`LARGE`, 2 × 4, 3 × 4, 4 × 2, 4 × 3) ; Plein écran (`FULL`, 4 × 4).
- **Contrat** (`HomeWidget`, `ui/home/HomeWidgets.kt`) : `applySize()` choisit la mise en page de la famille (`family`), jamais un simple étirement. Plus grand, le widget montre plus de choses ; plus petit, il garde l'essentiel (comme les widgets d'Apple). Les tailles de texte et d'image suivent la taille réelle de la vue, qui change avec le profil de rangées (`RowProfile`). Rien de lourd en plus : 18,2 ms par image (`docs/tablette-4.2.md`).
- **Fond** (#214) : toute carte de widget prend `HomeCard.background(context)` (`ui/home/HomeCard.kt`), jamais `c_home_card_bg` directement : la tuile du thème au style de Réglages > Thème > Widgets de l'Accueil (`Prefs.homeCardStyle`) : Voile (par défaut, `c_surface` à 42 %, sans filet), Sans filet (la tuile du thème, filet retiré), À même le fond (transparent au repos). Filet retiré dans les trois ; l'appui et le rayon restent ceux du thème (halo rose de Hush) ; l'écran Focus et l'écran Ordi gardent `c_home_card_bg` tel quel ; une tuile de la couleur du fond (Contraste élevé) reste telle quelle, son filet est sa seule limite.
- **Aperçu** : chaque widget a une classe d'exemple (`WidgetSample`, écrite à côté du widget, ex. `NoteSample`) rendue par `WidgetSamples.of(type)` (`ui/home/WidgetSamples.kt`, un bloc par famille de widgets) et dessinée par `showPreview(sample)`, appelé après `applySize()`. Le catalogue n'appelle ni `load()` ni `setActive()` : pas de réseau, pas de minuterie, constructeur compris.
- **Le catalogue d'ajout** (#179) : en mode Modifier, une case vide ou « Ajouter » ouvre `CatalogueView` (`ui/home/`), plein écran par-dessus l'Accueil. À gauche, les widgets que l'ordinateur actif offre, rangés par rayon (`CatalogueShelf`, ceux des issues #180 à #186), 3 suggestions en tête (`SUGGESTED`, retirées de leur rayon). À droite, la fiche du widget touché (`CatalogueSheet`), sans fenêtre de plus : un seul aperçu vivant à la fois, à la taille réelle d'une case de l'Accueil puis réduit d'une échelle commune à toutes les formes du widget ; sans exemple, une carte icône + nom. Flèches ou glissement d'une forme à l'autre, dans l'ordre de `SHAPE_ORDER` (par famille, de la plus petite à la plus grande), ouverte sur la forme d'ajout (`openingShape`). `shapeChoices` (fonction pure, `CatalogueModelTest`) dit pour chaque forme si elle tient à la case touchée ; sinon elle est grisée « Pas la place ici » et le bouton propose la première place libre, ou se désactive si la page n'en a pas. Retour ferme le catalogue sans quitter le mode Modifier.
- **Le test** : `WidgetRulesTest` (`app/src/test/.../ui/home/`) vérifie que chaque `WidgetType` accepte les 16 formes et a un aperçu. Les manques sont dans une liste d'exceptions par famille de widgets (`WidgetGapsHeure.kt` #180, `WidgetGapsListes.kt` #181, `WidgetGapsSon.kt` #182, `WidgetGapsOrdinateur.kt` #183, `WidgetGapsAppels.kt` #184, `WidgetGapsDev.kt` #185, `WidgetGapsPerso.kt` #186), une ligne par widget avec sa raison. Une exception tenue (le widget a ses 16 formes ou son aperçu) fait aussi casser le test : retirer la ligne. Un nouveau widget n'a pas d'exception.
- **Page de l'ordinateur et MCP** : ils lisent les formes que la tablette publie (`LayoutConfig`, `sizes` et `catalog`), sans liste en dur ; le schéma de `profils_ecrire` prend la forme comme un texte libre et c'est la tablette qui la vérifie (`LayoutConfig.parseLayout`). Test : `backend/e2e/local-config-profiles.spec.ts` (page de l'ordinateur).

### Veille à la présence

- **Veille à la présence** (#68, `presence/`, `Prefs.presenceSleep`, coupée par défaut) : Réglages > Tablette, sous « Atténuer l'écran la nuit ». La caméra avant (`PresenceCamera`, Camera2 sans aperçu) repère un mouvement ; sans présence pendant 5 minutes (`PresenceLogic.SLEEP_DELAY_MS`), l'écran s'endort, puis se réveille à l'arrivée. Tout est calculé sur la tablette : le plan de luminance de la plus petite image YUV (au moins 160×120, cadence la plus basse du capteur) est réduit à 32×24 octets (`MotionDetector.reduce`), une image sur 500 ms est analysée, les autres sont rendues sans être lues ; seul « mouvement ou non » sort, aucune image n'est copiée, envoyée ni gardée. `MotionDetector.moved` compare chaque image à la précédente : la moyenne (lumière qui change) est retirée, il faut plus de 2 % de pixels qui changent de plus de 24 niveaux. `PresenceLogic` (sans Android, l'heure est donnée) : un mouvement ou un toucher repousse la veille ; réveil par un toucher, par deux images en mouvement de suite, ou dès que l'écran sert (`MainActivity.frameBusy` : appel, Focus qui tourne, mode Caméra, document ouvert, boîte de dialogue…), et le délai ne court pas tant qu'il sert. « Veille » = voile noir (`presence_veil` de `view_presence.xml`, ajouté en dernier enfant du contenu : au-dessus du cadre photo ; couleurs `c_frame_bg`/`c_frame_text`, grain et motif du thème retirés dessous ; description TalkBack et clic qui réveille) + luminosité au minimum (`Screen.presenceAsleep`), pas la veille d'Android : la caméra n'y serait plus accessible, et l'écran de Mate reste allumé en permanence (`FLAG_KEEP_SCREEN_ON`). Le toucher qui réveille est avalé (`swallowTouch`), comme celui qui ferme le cadre photo. La caméra tourne seulement quand Mate est à l'écran, le réglage activé, la permission accordée (demandée à l'activation du réglage si elle manque ; accordée d'office en kiosque ; refusée, le réglage revient sur coupé) , le mode Caméra pas ouvert (une seule caméra à la fois sur la 4.2) et le verrou par code absent (fenêtre à part : voyant et voile y seraient cachés) ; elle s'arrête dans la demi-seconde si l'un d'eux apparaît et repart à la minute suivante. Caméra tombée ou introuvable : bandeau une seule fois, nouvel essai au plus tôt une minute après (`PresenceLogic.canStart`), sans boucle ; le mode Caméra qui ferme la sienne retarde de même la caméra de veille (`holdOff`). La fermeture est asynchrone : une nouvelle caméra, et celle du mode Caméra (`whenPresenceCameraFree`, `CameraFragment.startCamera`), n'ouvrent qu'après `onClosed` (délai de secours 2 s : l'appelant reprend la main mais le fil reste jusqu'à `onClosed`, y compris pour une caméra tombée) et les voyants restent jusque-là ; les rappels d'une caméra arrêtée sont ignorés (génération). Indicateur obligatoire (la 4.2 n'a pas de voyant) : icône caméra à l'accent dans la barre du haut (`TopBar.presenceEye`, visible en mode Modifier) et, pendant la veille et le cadre photo, voyant par-dessus tout (`presence_eye`). Caméra absente ou perdue : réglage grisé sans caméra avant ; en cours d'usage, bandeau « veille en pause » et l'écran se réveille. Pas encore mesuré sur la vraie tablette : charge processeur, seuils (24 niveaux, 2 %) et cadence.

### Performances

- **Performances** (`GET /system/perf`, `backend/src/perf.ts` pur, sources injectées par `os.ts`) : `cpu` et `ram` toujours, puis des champs facultatifs, absents quand ils sont illisibles et jamais inventés : `cpuTempC` (31/10 : entier 10–150 °C ; Mac Apple Silicon par `macmon pipe` (`src/mac/temperature.ts`, github.com/vladkens/macmon, MIT, sans `sudo`, à installer par `brew install macmon`, absent : rien) ; Windows par `MateCapteurs.exe` (`src/win/capteurs/`, LibreHardwareMonitorLib 0.9.6, MPL-2.0) qui écrit `%LOCALAPPDATA%\Mate\capteurs\cpu-temp.json` toutes les 2 s, lu par `src/win/capteurs.ts` (fichier de plus de 6 s : rien). Le pilote noyau PawnIO ne se lit qu'en administrateur : `scripts/capteurs-windows.ps1`, lancé par le bouton « Activer » du panneau (`POST /local/capteurs`, accord administrateur demandé une seule fois), installe PawnIO 2.2.0 (SHA-256 figé) et crée la tâche planifiée « MateCapteurs » (droits maximum, à l'ouverture de session) ; le compagnon la relance (`schtasks /run`, sans accord) quand le fichier est périmé), `fps` (31/10, #21 ; Windows avec carte AMD seulement : nombre entier du jeu au premier plan, `null` quand le lecteur marche mais qu'aucun jeu n'est mesuré, jamais 0 ; clé absente ailleurs, Mac compris, aucun moyen public d'y lire les FPS d'une autre appli). Lu par ADLX, le SDK d'AMD : `Native.Fps.cs` charge `amdadlx64.dll` du dossier système (installée avec le pilote, rien n'est livré) et appelle `IADLXPerformanceMonitoringServices::GetCurrentFPS`, le chiffre de l'overlay d'Adrenalin ; ne marche que dans la session de l'utilisateur, pas en SSH), `cpuWatts`, `gpuWatts` (W, une décimale, 0 à 1000 exclu 0 ; 01/11, #70 : Mac par `cpu_power` et `gpu_power` de la même lecture `macmon pipe`, partagée une seconde avec la température ; Windows par `MateCapteurs.exe` qui y ajoute « CPU Package » et le premier capteur Power d'une carte graphique, `gpuWatts` au niveau du relevé car le Mac n'a pas d'objet `gpu`), `cpuFanRpm` (tr/min entiers ; Windows seulement, ventilateur « CPU Fan » ou « CPU » de la puce Super I/O de la carte mère, donc absent sur les cartes dont LibreHardwareMonitor ne nomme que « Fan #1 » (on ne devine pas) ; 0 écarté ; absent sur Mac, `macmon` ne lit aucun ventilateur), `cpuMhz` (Windows, compteur PDH `Processor Frequency`), `gpu.vramUsedMb`/`vramTotalMb` (carte dédiée seulement : total DXGI, utilisé par le compteur `GPU Adapter Memory` du LUID de la carte), `disk` (`freeGb`/`totalGb` par `fs.statfs` de `/` ou `C:\`, `activity` 0-100 par `PhysicalDisk(_Total)\% Disk Time` sous Windows) et `net` (`upKBps`/`downKBps` : compteurs `Network Interface` sous Windows, deltas de `netstat -ib` sur les `en*` sur Mac). Chaque lecture est bornée à 1,5 s et normalisée (entiers, bornes, NaN et négatifs écartés). Windows : l'opération générique `counters` du pilote (`Native.Perf.cs`) lit une liste de chemins PDH anglais et rend la somme des instances valides (boucle locale et `isatap` exclues).
- **Courbe du widget** (01/11, #71) : mise en page « chiffres » (Moyen, Grand et Plein écran depuis #183) ; `PerfHistory` garde 150 relevés (un toutes les 2 s, soit 5 minutes) de processeur, carte graphique et mémoire, vidés quand la page est quittée ; `PerfSparkline` trace un trait par info cochée (processeur `c_text`, carte graphique `c_text_faint`, mémoire `c_text_dim`), de 0 à 100 %.
- **Les 16 formes** (#183) : une mise en page par famille, `perfLayout` (`PerfModel.kt`) : Pastille = un anneau, celui de la mesure cochée la plus chargée avec son nom dessous (variante B choisie par Ahmed) ; Ligne = les chiffres en 2 × 1, les barres au-delà ; Colonne = les barres empilées, les infos en texte dessous ; Bloc = les anneaux ; Grand et Plein écran = les chiffres (jusqu'à 96 sp) et la courbe. - **Ce qui consomme** (11/11) : `GET /system/perf/apps` (`backend/src/perf-apps.ts` pur, processus injectés par `os.ts` ; Windows : opération `processes` du pilote, compteurs PDH `\Process(*)\% Processor Time` lus avec `PDH_FMT_NOCAP100` (un processus dépasse 100 % d'un cœur) et `Working Set - Private`, comme le Gestionnaire des tâches ; Mac : `ps -Aco pcpu=,rss=,comm=`) rend les 5 applis les plus gourmandes, processus regroupés par appli (`chrome#3` → « Google Chrome », aides Mac `X Helper (…)` → « X », quelques noms d'exe traduits, `_Total`, `Idle` et la compression mémoire écartés), triées par la plus forte part de processeur ou de mémoire de la machine.
